# R18 · version single-sourcing, skill-topology cleanup, and sync tooling（2026-08-31）

> Full iteration record. Not read during normal work; current facts live in NOW and the authority
> contracts.

## Goal

Housekeeping after the `vibecoding_manager` rename and the R15 skill rename:
(1) make the kit version single-sourced so it cannot drift; (2) review and clean the three-skill
distribution topology (the manager skill nests a close-loop copy); (3) decide whether the current
skill-based packaging needs an MCP layer.

## Decisions

- **Version**: root `VERSION` (1.2.0) stays the single authority. The self-contained install skill
  cannot read the repo root when deployed to `$CODEX_HOME`, so it now carries its own bundled
  `VERSION`, and a new drift gate forces it to equal the root value. The `0.1.0` in
  `pyproject.toml` / `package.json` is the **scaffold seed version** for generated projects — kept
  independent from the kit version by design (a fresh user project must not claim the kit's version).
- **Skill topology**: the nested copies are intentional (self-contained distribution: the manager
  skill needs a close-loop payload to scaffold, the install skill bundles both skills to deploy from
  inside Codex). Optimization = remove leftover empty dirs, and turn the manual multi-copy sync into
  a scripted gate so drift stays fixable, not just detectable.
- **Packaging**: keep skill + stdlib Python scripts; do **not** add MCP yet (see Boundary and
  roadmap P8). Skills stay the orchestration/prompt layer; deterministic tools stay scripts.
  An MCP adapter is deferred until a second client or a resident runtime service actually needs it.

  one-click-installer docstring. Historical CHANGELOG rows and archives are left as records.
- Updated README project layout + new "Distribution & sync" section documenting the payload copies

## Boundary

- Packaging/MCP remains a **roadmap P8 decision**. Recommendation: adopt a "skill + MCP" split only
  when (a) a second agent client (Claude Code / Cursor / IDE) must call the same deterministic tools,
  or (b) P2+ runtime features need a resident process; the existing `tools/*.py` are already
  deterministic and MCP-ready, so the adapter would be thin. Not implemented this round.
- Runtime artifact store, context compiler, and behavior evaluation harness remain P2/P8 work.
