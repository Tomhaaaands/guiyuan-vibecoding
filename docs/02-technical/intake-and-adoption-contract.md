# 启动接入与渐进接管契约

## 目标

VCM 的第一次交互先确认“用户想做什么”，再判断当前目录与候选模板的关系。目录指纹只能
提供事实和“可能像什么”的提示，不能替用户决定项目类型、拓扑或接管方式。

## 交互顺序

1. **意图闸门**：询问产品目标；同时告知当前项目位置和默认项目名。位置和名称是可修正的
   上下文，不单独制造一次确认流程。
2. **项目只读盘点**：展示目录的基础概览、可能的项目形状、已存在的管理约定，以及基于
   产品描述的候选模板和目录结构。内部匹配分数、风险明细和逐工具诊断不进入人工输出。
   同一轮还扫描项目体量（排除依赖、缓存、构建产物和管理层）与候选数据目录/文件。小、中
   体量可以建议完全接管；大体量默认建议部分或渐进接管，但最终选择仍由用户确认。
3. **接管选择**：用户在四个选项中选择：
   - 完全接管：按确认的模板建立管理结构，归档旧管理层；先生成项目目录之外的迁移计划，
     用户确认后才迁移数据、修复明确的路径依赖并写入完全接管标识；
   - 部分接管：只接管管理流程，不改造目录、不重构业务代码；
   - 渐进接管：本迭代保留老流程，从新需求开始并行记录；
   - 放弃接管：当前项目不使用 Guiyuan Vibecoding。
4. **全机环境授权**：用户明确授权后，才做整台电脑的只读元数据盘点：Agent、共享 Skill
   目录、Python/Node 环境、UV、GitHub CLI。盘点不安装、不切换解释器、不修改 PATH 或配置。
5. **环境选择与执行**：在用户选定 Python/Node、UV 时机和依赖策略后，才允许安装、创建
   `.venv`、npm 安装、Git/Skill 写入等动作。
6. **成功回报**：只有执行和验证都完成后，才报告接入成功；未完成事项必须单列。

## 体量与迁移边界

- 小体量：不超过 1,000 个文件且不超过 100 MiB；
- 中体量：不超过 10,000 个文件且不超过 2 GiB；
- 其他情况为大体量。阈值是可审计的初始建议，不替用户作最终决定。
- 数据映射只覆盖模板中存在的明确目标（例如 `knowledge -> data/knowledge`、
  `vector -> data/vector`）；未知数据保留原位并列出待人工处理。
- 路径修复只改写计划中明确的文本引用；执行前校验文件哈希，原文件保存在可回滚备份中。
- 完全接管成功后才写 `.guiyuan-vibecoding/takeover.json` 与 `FULL_TAKEOVER.md`；未确认迁移
  计划时不得声称已完成完全接管。

## 机器接口

```text
python skills/guiyuan-vibecoding/scripts/bootstrap.py <folder> \
  --mode assess --name <name> --intent "<product description>" --json
```

上面的命令只读并将 JSON 保存到项目目录之外。用户授权整机盘点后追加
`--environment-scan`。人工摘要只显示基础事实、候选模板、建议目录与四档接管选项；JSON
可以保留供后续 `--mode adopt --assessment <json>` 使用的机器字段。

`progressive` 是渐进接管的正式机器值；旧自动化传入的 `defer` 作为兼容别名保留。两者都
不会替换既有管理文件，只记录一份决策收据。

## 功能模块目录

评估摘要会引用 VCM 的功能模块目录，帮助用户理解管理层将覆盖哪些职责：项目接入与生命
周期、需求接收与分析、权威工件与上下文、规划与任务编排、执行验证与交付、反思与经验回
流，以及模板与能力 Overlay。项目候选模板的物理目录（例如 `src`、`app`、`apps`、
`tests`）另行列出，二者不可混为业务模块事实。
